# REAPER: primary editing reference

Evidence: DOCUMENTED, using the official feature page, ReaScript guide and API generated by REAPER 7.82. A direct HTTP check verified nineteen relevant API anchors and seven attribute names; [the receipt](evidence/reaper-api-inspection.json) records the documentation hash. The online API warns it may lag an installed build. The guide index advertises a 7.81 manual; that PDF's body was not successfully retrieved here. No REAPER binary or live project was inspected.

## Documented behaviour

REAPER combines media placement, trims, splits, slip edits, fades, overlapping layers, take lanes and comping. Tracks support processing and routing, including folder-based bussing. Track/take controls and effects can be automated. Render selections combine tracks, items and regions; the region matrix pairs chosen tracks with chosen regions. Batch instructions and filename substitutions support repeatable delivery. These are published capabilities, not measured results. [REAPER features](https://www.reaper.fm/about.php)

The public interface exposes the boundaries that matter for reconstruction:

| Interface | Observable contract to study |
|---|---|
| `GetMediaItemInfo_Value` | Item position, length, volume and fades |
| `GetMediaItemTakeInfo_Value` | Source offset, gain and playback rate per take |
| `GetMediaItemTake_Source` | A take's source reference |
| `SplitMediaItem` | Left item retained; right item returned; failure possible |
| `CreateTrackSend` / `SetTrackSendInfo_Value` | Explicit routing and send parameters |
| `InsertEnvelopePointEx` | Automation-point insertion |
| `SetRegionRenderMatrix` | Region/track membership and output channel selection |

These names establish public data/control concepts; they do not reveal REAPER's private storage or DSP algorithms. [ReaScript API](https://www.reaper.fm/sdk/reascript/reascripthelp.html)

ReaScript can invoke actions and API calls through EEL2, Lua or Python. Lua/EEL2 are embedded; Python requires separate configuration. Scripts can persist project metadata and group edits into named undo blocks. REAPER can generate API documentation from the running version, which should be captured before an empirical probe. [ReaScript guide](https://www.reaper.fm/sdk/reascript/reascript.php)

## Proposed Soundr reconstruction

Use one timeline model and a small set of validated operations. The UI, keyboard actions, batch actions and MCP will call the same command service. A macro is a transaction containing ordinary commands; it must expose its affected clips and either apply completely or leave the revision unchanged.

At unity playback rate and a common project sample rate, define a clip as `(sourceId, sourceIn, timelineStart, duration)` with half-open ranges:

| Operation | Soundr rule |
|---|---|
| Move by `d` | Change `timelineStart` only; preserve the source range |
| Trim left by `d` | Add `d` to source-in and timeline start; subtract it from duration |
| Trim right by `d` | Subtract `d` from duration |
| Slip by `d` | Change source-in only; check both source bounds |
| Split at local `d` | Preserve the left ID; create a right ID at source-in/start plus `d`; remap fades/envelopes |
| Fade | Store duration and curve as metadata; apply in playback/render |
| Duplicate | Create a new clip ID referencing the same immutable source |

These are Soundr's proposed invariants, not an assertion about REAPER implementation. Commands reject empty/out-of-bounds ranges. Negative moves cannot wrap around. A split's union covers the original range exactly; neither child reads beyond the original source interval. Editing a resampled derivative must preserve its original-source lineage.

Tracks need explicit overlap policy. An ambience/effects track can mix overlapping clips. A dialogue take group chooses one active candidate; changing that choice preserves all rejected candidates. Phrase comping later creates an arrangement of references to selected source segments, not destructive concatenation of the original recordings.

Represent folder hierarchy and audio routing separately. A convenient UI group may offer to create routing, but collapsing or reordering a folder must not silently change the signal graph. Start with cycle-free tracks/buses and explicit pre/post-fader sends. Intentional feedback routing is deferred.

Keep clip gain before track processing and mix automation at the track/bus stage. Store effect order, bypass state, parameter values and eventual engine/plugin identity. Missing processors must appear in project diagnostics and block a purportedly equivalent final render.

Model render selection as a range-by-output matrix. Each selected cell becomes a fully specified job with a picture revision, sample range, buses, channel layout, sample rate, bit depth, tail/normalisation/dither policies and collision-safe destination. Save the job before execution. Save a manifest with hashes and all omissions after execution.

## What the scene experiment must resolve

- Which actions and modifier keys provide the fastest precise placement and take comparison?
- How do selected takes, overlapped lanes, split fades and item envelopes behave at edit boundaries?
- Which automation moves with media during ripple edits, and which stays at absolute time?
- What do pre/post-fader sends, latency compensation and rendered effects contribute to each stem?
- Does save/reopen preserve source references, render selections and all offsets exactly?
- Do repeated renders match decoded samples under fixed settings? Container metadata and dither need separate treatment.

Use the [shared scene protocol](../acceptance/SCENE_BENCHMARK.md). A future read-only ReaScript capture should enumerate tracks, source paths, item/take attributes, routes, envelopes, regions and matrix membership before and after each operation. Capture through documented APIs, never a guessed `.RPP` parser. Soundr's own project format should remain independent of REAPER.
